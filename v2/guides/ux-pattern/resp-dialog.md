정보를 인지시키거나, 되돌리기 어려운 동작 전에 의사를 확인받는 딤 팝업입니다.
 인지만 받는 Alert과 취소·실행을 묻는 Dialog로 나눕니다.

#### 개요 · 언제 쓰나요?

확인·경고 다이얼로그는 뒤 화면을 딤으로 막고 중앙에 띄우는 팝업입니다.
 같은 딤 팝업이라도 무엇을 하려는지에 따라 종류가 갈립니다.

| 종류 | 사용 시점 | 푸터 버튼 | 헤더 닫기(X) |
| --- | --- | --- | --- |
| 정보 Alert | 결정할 것이 없고 인지만 받을 때 | 실행 1개 | 없음 |
| 확인 Dialog | 실행할지 말지 결정이 필요할 때 | 취소 + 실행 | 있음 |
| 위험 Dialog | 되돌릴 수 없는 동작을 실행할 때 | 취소 + 위험색 실행 | 있음 |

**한 줄 판단**: 알리기만 하면 Alert · 물어야 하면 Dialog · 되돌릴 수 없으면 위험 Dialog입니다.

팝업 안에서 입력·선택 작업을 하는 유형(Modal)은 [상세 팝업](popup.html)에서 다룹니다.

###### ✓ 이럴 때 사용합니다

- 되돌릴 수 없는 동작(삭제·일괄처리)을 실행하기 전에 의사를 확인받을 때
- 저장에 부작용이 따라올 때(다른 값이 함께 바뀌거나 즉시 노출될 때)
- 결정할 것이 없지만 그냥 지나치면 안 되는 결과를 인지시킬 때
- 사용자가 눌러 실행한 처리가 실패했거나 실패 건수가 갈린 결과를 알릴 때

###### ✕ 다른 패턴을 사용합니다

- 단순 성공 알림(저장 완료 등) → [토스트·스낵바](resp-toast.html)
- 되돌릴 수 있게 만들어 되돌리기를 제공할 때 → [토스트·스낵바](resp-toast.html)의 실행 취소
- 시스템이 알려오는 상태·경보(세션 만료 · 권한 없음 · 자동 저장 실패 · 연결 끊김) → [전역 예외 화면](resp-error-page.html)
- 팝업 안 폼의 입력값 검증 실패 → [폼 유효성 체크](resp-form-validation.html)

핵심 원칙확인 다이얼로그는 되돌릴 수 없거나, 영향 범위가 보이지 않거나, 부작용이 따라올 때만 씁니다.
 묻는 것은 다이얼로그, 알리는 것은 토스트입니다.
 결정할 것이 없으면 화면을 막지 않습니다.

#### 구성요소

Alert과 Dialog는 제목 · 본문 · 푸터라는 같은 골격을 씁니다.
 갈리는 곳이 위 표의 푸터 버튼과 헤더 닫기(X) 둘뿐이므로, 컴포넌트는 하나로 두고 값(prop)만 달리 받습니다.

1. 제목하려는 행위를 그대로 씁니다. 모호한 질문형(‘정말 하시겠어요?’)을 쓰지 않습니다.
2. 본문실행하면 무엇이 어떻게 되는지, 되돌릴 수 있는지를 적습니다. 영향 범위가 있으면 건수를 밝힙니다.
3. 취소왼쪽에 둡니다. 아무 일도 일어나지 않는 쪽이 기본값이므로 여기에 기본 포커스를 둡니다.
4. 실행오른쪽에 둡니다. 라벨은 동사로 씁니다. 되돌릴 수 없는 동작은 위험색으로 구분합니다.
5. 닫기Dialog의 우측 상단에 둡니다. 취소와 같은 동작이며 아무 일도 일어나지 않습니다. Alert은 확인 하나가 곧 닫기이므로 두지 않습니다.

#### 핵심 동작 · 상태

트리거를 누르면 곧바로 실행하지 않고 다이얼로그로 한 번 더 묻습니다.
 실행 버튼을 누르면 실행하고, 취소를 누르면 닫고 아무것도 하지 않습니다.

##### 묻는 기준

확인 다이얼로그는 사용자의 흐름을 끊습니다.
아래 넷 중 하나라도 해당할 때만 씁니다.
 하나도 해당하지 않으면 묻지 않고 실행한 뒤 토스트로 알립니다.

| 조건 | 설명 | 예 |
| --- | --- | --- |
| 되돌릴 수 없습니다 | 실행하면 복구가 안 되거나 비용이 듭니다 | 삭제 · 해지 · 마감 · 발송 |
| 영향 범위가 보이지 않습니다 | 몇 건에 작용하는지 눌러야만 알 수 있습니다 | 선택 00건 일괄 처리 |
| 부작용이 따라옵니다 | 값만 저장되지 않고 다른 것이 함께 바뀝니다 | 이동하면 대상 그룹 요금 조건이 함께 적용 |
| 흐름이 끊깁니다 | 사용자가 시작하지 않은 이탈·손실을 시스템이 막습니다 | 입력 중 화면 이탈 |

묻지 않는 쪽이 맞는 경우는 아래와 같습니다.

- 되돌릴 수 있고 부작용이 없는 저장
- 폼 안에서 내용을 다 보고 있는 상태의 저장
- 추가·등록처럼 폼을 띄우는 동작

##### 결과 알림

다이얼로그와 토스트는 역할과 시점이 다릅니다.
그래서 겹치지 않습니다.

- **다이얼로그**: 실행 전에 묻습니다.
- **토스트**: 실행 후에 알립니다.
- **한 동작에 둘 다**: 정상입니다. 확인 Dialog → 실행 → 토스트 순으로 나옵니다.
- **정보 Alert**: 그 자체가 결과 통지이므로 토스트를 겹치지 않습니다. 토스트로 충분한 내용이면 Alert을 쓰지 않습니다.

실패는 토스트가 받지 않습니다.

토스트와 스낵바는 시간이 지나면 사라지므로, 실패를 단독으로 담으면 놓친 사용자가 다시 볼 방법이 없습니다.
 그래서 사용자가 눌러서 생긴 처리 실패와 실패 건수는 정보 Alert이 받습니다.
 Alert은 사용자가 확인을 누를 때까지 남고, 원인과 다음 행동을 여러 줄로 담을 수 있습니다.

사용자가 시키지 않은 것은 Alert이 받지 않습니다.

자동 저장 실패 · 세션 만료 임박 · 연결 끊김처럼 시스템이 알려오는 상태는 [전역 예외 화면](resp-error-page.html)의 전역 안내 메시지가 받습니다.
 사용자가 시작한 일이 아니므로 화면을 막지 않습니다.
 같은 저장 실패라도 사용자가 ‘저장’을 눌렀으면 Alert, 시스템이 자동 저장을 돌렸으면 전역 안내 메시지입니다.

되돌릴 수 있는 동작은 반대입니다.

묻지 않고 실행한 뒤 스낵바로 ‘실행 취소’를 줍니다.
 자세한 분담은 [토스트·스낵바](resp-toast.html)의 **되돌릴 수 있습니까** 표에 있습니다.

다이얼로그가 열려 있는 동안에는 토스트·스낵바를 띄우지 않습니다.
 닫힌 뒤에 띄웁니다.

##### 열림·닫힘 규칙

| 항목 | 규칙 |
| --- | --- |
| Esc | 전 유형에서 닫습니다. 취소와 같습니다. 여러 겹이 열려 있으면 한 번에 한 겹만 닫습니다 |
| 딤 클릭 | 닫습니다. 닫는 쪽이 아무 일도 일어나지 않는 안전한 기본값입니다 |
| 헤더 닫기(X) | Dialog의 우측 상단에 둡니다. 취소와 같은 동작입니다. Alert에는 두지 않습니다 |
| 초기 포커스 | 위험·의사결정은 취소, 인지는 실행에 둡니다 |
| 포커스 이동 | Tab이 팝업 밖으로 나가지 않습니다. 딤과 반드시 같이 구현합니다 |
| 닫은 뒤 | 열었던 트리거로 포커스를 되돌립니다 |
| 스크롤 | 열려 있는 동안 뒤 페이지는 스크롤되지 않습니다 |
| 푸터 정렬 | 우측 정렬입니다. 취소가 왼쪽, 실행이 오른쪽이고 강조 버튼이 맨 오른쪽입니다 |
| 버튼 수 | 푸터는 최대 2개입니다 |
| 버튼 라벨 | 실행 버튼은 동사(삭제·저장·이동)로 씁니다. 인지형만 확인을 씁니다 |
| 폭 | Alert과 Dialog는 같은 위계이므로 같은 폭을 씁니다. 치수는 디자인 가이드가 소유합니다 |

#### 실제 예시

행을 선택하고 아래 세 버튼을 눌러 세 유형을 차례로 확인합니다.
 버튼은 다이얼로그를 띄우기 위한 트리거이며, 어떤 버튼을 어디에 두는지는 이 문서의 규정이 아닙니다.

1. **선택 삭제** → 위험 Dialog
2. **선택 이동** → 확인 Dialog
3. **일괄 처리** → 정보 Alert

세 유형이 각각 어떤 조건에서 나왔는지는 위 **묻는 기준** 표에 있습니다.

행을 선택한 뒤 삭제 · 이동 · 일괄 처리를 눌러 세 유형을 차례로 확인합니다.

확인·경고 다이얼로그 · 세 유형 확인새 탭에서 크게 보기※ 예시 이미지 — 레이아웃/디자인은 확정 아님. 패턴 구조만 참고.
#### Do / Don't

###### Do · 이렇게 합니다

- 제목에 하려는 행위를 씁니다. (예. ‘항목 삭제’)
- 되돌릴 수 없는 동작은 영향 범위(건수)와 복구 불가를 본문에 함께 밝힙니다.
- 실행 버튼 라벨을 동사로 씁니다. (예. 삭제 · 저장 · 이동)
- 취소를 왼쪽, 실행을 오른쪽에 두고 푸터는 최대 2개로 둡니다.
- 위험 동작의 실행 버튼을 위험색으로 구분하고 기본 포커스를 취소에 둡니다.
- 실행 결과는 토스트로 알립니다.
- 눌러서 생긴 실패와 실패 건수는 정보 Alert으로 인지시킵니다.

###### Don't · 이건 피합니다

- 행위가 안 보이는 제목을 쓰지 않습니다. (예. ‘정말 하시겠어요?’)
- 단순 성공 알림을 다이얼로그로 띄우지 않습니다. (→ 토스트·스낵바)
- 정보 Alert에 토스트를 겹쳐 띄우지 않습니다. 같은 내용을 두 번 알리게 됩니다.
- 값만 바뀌는 저장에 확인을 붙이지 않습니다. 확인 문구를 읽지 않고 누르는 습관이 생깁니다.
- 추가·등록 버튼에 확인 다이얼로그를 붙이지 않습니다. 폼을 띄우는 트리거입니다.
- 푸터 버튼을 3개 이상 늘리지 않습니다.
- 실패를 자동으로 사라지는 토스트에 맡기지 않습니다. 놓치면 다시 볼 방법이 없습니다.

노드 캔버스에서 되돌릴 수 없는 동작 전에 의사를 확인받는 딤 팝업입니다.
 딤이 캔버스가 아니라 화면 전체를 덮고, 묻기 전에 노드 안에서 먼저 예고합니다.

#### 개요 · 언제 쓰나요?

**한 줄 판단**: 되돌릴 수 없으면 다이얼로그 · 되돌릴 수 있으면 묻지 않고 넘깁니다.

노드 UI는 단계를 밟는 화면이라 확인을 붙일 자리가 많아 보입니다.
 그래서 일반 UI 탭의 **묻는 기준** 표를 그대로 적용하고, 실제로 걸리는 자리만 남깁니다.

| 자리 | 왜 묻습니까 | 유형 |
| --- | --- | --- |
| 데이터 저장 | 되돌릴 수 없습니다 | 확인 Dialog |
| 취소 업무 생성 | 되돌릴 수 없고, 영향이 뒤 노드까지 갑니다 | 위험 Dialog |
| 단계 전환 | 넷 중 어디에도 걸리지 않습니다 | 묻지 않습니다 |

각 다이얼로그가 언제 뜨고 무엇을 담는지는 아래 **핵심 동작 · 상태**에서 하나씩 다룹니다.

저장 시점 · 수정 제한 · 취소 업무의 규정은 [역방향 진행](node-flow-reverse.html)이 갖습니다.
 이 탭은 그 지점에서 다이얼로그가 어떻게 묻는지만 다룹니다.

###### ✓ 이럴 때 사용합니다

- 데이터 저장으로 그 단계가 확정되어 노드에서 수정할 수 없게 될 때
- 취소 업무를 생성해 뒤 노드를 진행 불가로 되돌릴 때
- 입력 중인 사이드 패널을 닫아 값이 사라질 때

###### ✕ 다른 패턴을 사용합니다

- 다음 단계로 넘어가는 전환 → 묻지 않고 넘깁니다
- 부수 동작이 끝났다는 통지 → [토스트·스낵바](resp-toast.html)의 노드 UI 탭
- 그 노드 처리의 결과 · 사유 → 노드 안 결과 배너
- 입력값이 규칙에 맞지 않을 때 → [폼 유효성 체크](resp-form-validation.html)의 노드 UI 탭

핵심 원칙막고 물을 것만 다이얼로그에 맡깁니다.
 단계마다 물으면 읽지 않고 누르는 습관이 생겨 정작 저장 지점에서 무력해집니다.

#### 구성요소

Alert과 Dialog의 골격은 일반 UI 탭이 규정합니다.
 노드 UI에서 더해지는 것은 다이얼로그를 놓는 자리와 묻기 전에 알리는 자리입니다.

1. 딤캔버스가 아니라 화면 전체를 덮습니다. 사이드 내비게이션 바와 AI Communicator까지 함께 막힙니다.
2. 다이얼로그화면 중앙입니다. 캔버스를 확대·축소하거나 드래그해 옮겨도 따라가지 않습니다.
3. 노드 안 예고이 노드를 완료하면 무엇이 확정되는지 미리 알립니다. 다이얼로그가 첫 통보가 되지 않게 하는 자리입니다.
4. 트리거노드 안 버튼과 액션바 버튼입니다. 어느 쪽을 눌러도 다이얼로그는 같은 자리에 같은 모양으로 뜹니다.

#### 핵심 동작 · 상태

##### 어디까지 덮습니까

기준은 캔버스가 아니라 화면입니다.

| 항목 | 노드 UI |
| --- | --- |
| 딤 범위 | 화면 전체 · 사이드 내비게이션 바와 AI Communicator까지 |
| 다이얼로그 자리 | 화면 중앙 |
| 캔버스를 확대 · 축소했을 때 | 배율을 따르지 않고 같은 크기로 남습니다 |
| 캔버스를 드래그해 옮겼을 때 | 따라 움직이지 않습니다 |
| 사이드 패널 · 모달이 열려 있을 때 | 딤이 그 위를 덮고 다이얼로그가 가장 위에 옵니다 |

딤을 화면 전체로 두는 이유는 둘입니다.

- 캔버스만 덮으면 사이드 내비게이션 바로 다른 메뉴에 들어갈 수 있습니다. → 묻고 있는 것에 답하지 않은 채 화면을 떠나게 됩니다.
- 캔버스는 확대 · 축소되고 드래그로 옮겨집니다. → 다이얼로그가 캔버스 안에 있으면 배율을 따라 작아져 읽을 수 없게 됩니다.

[토스트·스낵바](resp-toast.html)의 노드 UI 탭과 반대입니다.
 토스트는 알리고 지나가므로 캔버스에 딸리고, 다이얼로그는 막고 묻으므로 막을 대상 전체를 덮습니다.

##### 데이터 저장은 어떻게 묻습니까

저장이 걸린 노드에서 실행 버튼을 누르면 뜹니다.
 누른 그 자리에서 처음 알리는 것이 아니라, 노드 안 예고 문구가 미리 알려 둔 것을 마지막으로 확인받습니다.

| 항목 | 데이터 저장 |
| --- | --- |
| 뜨는 때 | 저장이 걸린 노드에서 실행 버튼을 누를 때 |
| 제목 | ‘데이터 저장’ · 하려는 행위 그대로 |
| 본문 | 어느 단계까지 저장되는지 · 저장한 뒤 무엇을 못 하게 되는지 |
| 푸터 | 취소 + 저장 |
| 실행하면 | 그 단계까지 확정되고 노드에서 직접 고칠 수 없게 됩니다 |
| 취소하면 | 누르기 전 그대로입니다. 선택값도 노드 상태도 바뀌지 않습니다 |

예고가 먼저입니다.
 다이얼로그는 마지막 관문이지 첫 통보가 아닙니다.

- 노드 안 예고 문구가 완료하면 무엇이 확정되는지 미리 알립니다. → 노드 UI는 단계를 밟는 화면이라 미리 알릴 자리가 노드 안에 있습니다.
- 실행 버튼 라벨도 함께 예고합니다. → 버튼 이름은 업무마다 다르지만, 누르면 저장이 확정된다는 것이 라벨에서 읽히게 씁니다. (예. ‘저장하고 다음’ · ‘저장하고 완료’)
- 다이얼로그 본문은 예고와 같은 것을 말합니다. → 예고에 없던 조건을 여기서 처음 꺼내면 사용자는 앞에서 잘못 판단한 셈이 됩니다.

다이얼로그가 뜬 뒤의 화면은 위 **구성요소**의 그림과 같습니다.

##### 취소 업무 생성은 어떻게 묻습니까

이미 저장돼 노드에서 고칠 수 없는 단계에서 ‘수정 요청’을 누르면 뜹니다.
 되돌릴 수 없는 데다 뒤 노드까지 막으므로 위험 Dialog입니다.

| 항목 | 취소 업무 생성 |
| --- | --- |
| 뜨는 때 | 저장된 노드에서 ‘수정 요청’을 누를 때 |
| 제목 | ‘취소 업무 생성’ · 하려는 행위 그대로 |
| 본문 | 왜 직접 고칠 수 없는지 · 뒤 노드 몇 개가 진행 불가가 되는지 |
| 푸터 | 취소 + 업무 생성(위험색) |
| 실행하면 | 취소 업무가 생기고 뒤 노드 00개가 진행 불가가 됩니다 |
| 취소하면 | 저장된 상태 그대로입니다. 뒤 노드도 그대로 진행할 수 있습니다 |

영향 범위는 노드 개수로 밝힙니다.
 일반 UI가 ‘선택 00건’으로 말하는 자리에서 노드 UI는 ‘뒤에 오는 노드 00개’로 말합니다.
 노드 UI에서 파급이 가는 대상은 행이 아니라 단계입니다.

- 실행한 결과는 노드 안 결과 배너가 받아 노드에 남습니다. → 다이얼로그는 실행 전에 한 번 묻고 사라지므로 사유를 보관하지 않습니다.
- 진행 불가가 된 뒤 노드가 어떻게 보이는지는 이 문서가 정하지 않습니다. → 표기 규정은 [노드형 화면](layout-node.html)과 [역방향 진행](node-flow-reverse.html)이 갖습니다.
- 실행 버튼 라벨에 ‘취소’를 넣지 않습니다. → 왼쪽 취소 버튼과 같은 말이 한 푸터에 두 번 나오므로, 제목이 이미 말한 부분을 덜어 ‘업무 생성’으로 줄입니다.

##### 무엇을 묻지 않습니까

노드 UI에서 자주 어긋나는 자리는 둘입니다.

- 단계를 넘길 때마다 묻지 않습니다. → 노드가 열 개면 열 번 막히므로, 되돌릴 수 있는 전환은 넘기고 액션바 안내 문구가 다음 지시를 받습니다.
- 처리할 수 없다는 결과를 Alert으로 알리지 않습니다. → 확인을 누르면 사유가 사라지는데 노드는 여전히 막혀 있으므로, 노드 안 결과 배너가 받습니다.

##### 일반 UI 탭과 같은 것

아래는 노드 UI에서도 같으므로 일반 UI 탭이 규정합니다.

| 무엇 | 일반 UI 탭의 어디 |
| --- | --- |
| 세 유형과 푸터 버튼 구성 | 개요 |
| Esc · 딤 클릭 · 초기 포커스 · 포커스 트랩 | 열림·닫힘 규칙 |
| 푸터 정렬 · 버튼 수 · 치수의 소유 | 열림·닫힘 규칙 |

골격과 묻는 기준은 위 **구성요소** · **개요**에서 이미 일반 UI 탭으로 넘겼습니다.

#### 실제 예시

이 탭에는 눌러 보는 예시 화면을 두지 않습니다.
 위 **핵심 동작 · 상태**에 넣은 국면 화면이 예시를 겸합니다.
 확인할 곳은 자리 · 딤 범위 · 예고 · 파급 범위 · 묻지 않는 것 다섯 가지입니다.

#### Do / Don't

###### Do · 이렇게 합니다

- 딤을 화면 전체에 걸고 다이얼로그를 화면 중앙에 둡니다.
- 다이얼로그를 캔버스 밖에 두어 배율과 이동을 따르지 않게 합니다.
- 묻기 전에 노드 안 예고 문구와 버튼 라벨로 먼저 알립니다.
- 다이얼로그 본문에 예고와 같은 것을 씁니다.
- 영향 범위를 뒤에 오는 노드 개수로 밝힙니다.
- 실행한 결과는 노드 안 결과 배너에 남깁니다.

###### Don't · 이건 피합니다

- 딤을 캔버스에만 걸지 않습니다.
- 단계를 넘길 때마다 확인을 붙이지 않습니다.
- 예고에 없던 조건을 다이얼로그에서 처음 꺼내지 않습니다.
- 처리할 수 없다는 결과를 Alert으로 알리지 않습니다.
- 실행 버튼 라벨에 ‘취소’를 넣지 않습니다.
- 영향 범위를 건수로만 말하지 않습니다.
