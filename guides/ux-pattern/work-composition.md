요구사항을 받으면 페이지를 몇 개로 자를지와 각 페이지를 어떤 유형으로 만들지를 정합니다.
분절된 업무를 잇는 방법은 [업무 연결](work-connect.html)이 규정합니다.

#### 개요 · 언제 쓰나요?

업무를 크게 묶으면 화면 하나가 여러 업무를 떠안아 목적이 흐려집니다.
반대로 잘게 자르기만 하면 사용자가 업무를 옮겨 다니며 같은 조회를 반복합니다.
이 문서는 요구사항을 페이지로 자르고 각 페이지의 유형을 정하는 기준을 규정합니다.

###### ✓ 이럴 때 사용합니다

- 새 요구사항을 받아 페이지를 몇 개로 자를지 정하는 경우
- 그 페이지를 일반형 · 노드형 · 특수형 중 어떤 유형으로 만들지 고르는 경우
- 무엇이 이 업무에 속하고 무엇이 다른 업무인지 가르는 경우

###### ✕ 다른 패턴을 사용합니다

- 분절된 업무를 서로 잇는 방법 → [업무 연결](work-connect.html)
- 한 화면 안에서 앞뒤 단계로 이어지는 업무 → [다단 구성](layout-columns.html)

#### 결정 순서

요구사항을 받으면 아래 순서로 정합니다.
앞의 결정이 뒤의 결정을 좁히므로 순서를 지킵니다.

1. **업무 단위** — 이 요구사항을 처리하려면 페이지가 몇 개 필요하고 각 페이지에 무엇이 속하는지 결정합니다. 최소 단위로 분해한 뒤 대상·맥락 두 기준으로 그룹화합니다.
2. **화면 유형** — 각 페이지를 어떤 유형의 화면으로 만들지 결정합니다. 표준 규격 밖의 도구인지(특수형) 먼저 보고, 나머지는 진행이 선형인지(선형성)로 판정합니다.
3. **연결** — 분절된 업무 사이를 어떻게 이어 전체 목적의 맥락을 유지할지 결정합니다.

각 유형의 화면을 어떻게 구성하는지는 유형별 규격 문서가 규정합니다.

#### 1. 업무 단위 기준

##### 기본 원칙

- 한 페이지는 독립적으로 완결되는 하나의 업무 단위(Business Task)를 담습니다.
- 업무의 범위는 추상적인 직관에 의존하지 않고, 요구사항을 최소 단위(Task Atom)로 분해한 뒤 그룹화하여 정의합니다.

##### 업무 단위 수립 3단계

1. 1단계 — 원자화 (Decomposition)요구사항을 더 이상 쪼갤 수 없는 최소 기능 단위(Action Item)로 분해합니다. 이 단계에서는 UI·화면 구조를 고려하지 않고 무엇을 수행하는가에만 집중합니다.
2. 2단계 — 그룹화 (Grouping)분해된 기능 단위들이 아래 두 기준을 **모두** 만족할 때 하나의 업무 단위로 그룹화합니다. 하나라도 어긋나면 그룹화하지 않고 남겨 둡니다.**대상 (Domain Context)**: 동일한 핵심 엔티티를 다루는가. ‘회원정보’와 ‘계약정보’는 대상이 달라 분리합니다.**맥락 (Purpose Context)**: 동일한 업무 목적을 공유하는가. 목적이 다르면 같은 대상을 다뤄도 분리합니다.
3. 3단계 — 자립성 검증 (Self-containment Check)그룹화된 단위가 사용자 관점에서 목적을 완결짓는지 검증하고, 이 페이지가 담을 범위를 확정합니다. 완결은 DB 저장 시점이 아니라 사용자가 목적을 달성했다고 인식하는 시점이며, 임시 저장이나 단계별 보존은 완결이 아닙니다.**이미 존재하는 업무**: 새로 만들지 않고 [Cross-linking](work-connect.html) · [Task Flow](work-connect.html) · 공통 기능 모듈로 연결하도록 설계해 범위에서 제외합니다.**그룹화되지 않고 남은 기능 단위**: 단독으로 완결되지 않으면 팝업 등 비맥락적 UI로 표현합니다. (예. 참고성 조회)**확정한 업무 단위**: 독립된 URL을 갖는 페이지로 정의하고, 업무의 대상과 목적이 드러나는 명칭을 부여합니다.

#### 2. 화면 유형 기준

유형은 그 업무를 **어떤 구조로 진행하는지**로 정합니다.
진행이 정해진 경로를 따르는지 아닌지를 선형성이라고 합니다.
아래 세 질문을 순서대로 물어 하나로 확정합니다.

1. 표준 규격 밖의 도구입니까? → 특수형 (Special UI)아래 두 조건에 **모두** 해당할 때만 특수형입니다.**독립적 과업 완결성**: 과업의 진행이 그 화면 안에서 완결됩니다. 앞 업무의 작업 상태를 이어받아 계속하지 않습니다. (값을 주고받는 것은 별개입니다)**전문 툴·작업장 성격**: 단순 조회·입력이 아니라 복잡한 데이터 조작·설정·파일 처리·배치 작업을 수행합니다.못 미치면 특수형으로 빼지 않고 다음 질문으로 넘어갑니다. 화면 규격은 [특수형 화면](layout-special.html)이 규정합니다. (예. 요금제 시뮬레이터)
2. 진행이 선형입니까? → 노드형 (Node UI)정해진 경로를 따라가야 하는 업무입니다. 되돌아가거나 갈래가 나뉘어도 경로 자체가 정해져 있으면 선형입니다. 가르기 어려우면 아래 「노드형 vs 일반형」을 봅니다. 화면 규격은 [노드형 화면](layout-node.html)이 규정합니다. (예. 요금제 변경 · 신규개통)
3. 둘 다 아닙니까? → 일반형 (Standard UI)정해진 경로가 없어 사용자가 순서를 정하는 업무입니다. 조회·등록·수정을 오가며 반복하고, 앞 단계가 끝나야 다음이 열리는 의존이 없습니다. 화면 규격은 [일반형 화면 구조](layout-work.html)가 규정합니다. (예. 게시판)

- **특수형을 가장 먼저 묻습니다**: 특수형은 유형 선택이 아니라 표준 규격을 벗어나겠다는 선언입니다. 선형·비선형이라는 축 자체를 벗어나므로 먼저 걸러야 뒤 판단이 헛돌지 않습니다.
- **완전한 권한을 가진 상태로 판정합니다**: 조회·상세·수정·생성 중 무엇을 제공할지는 권한이 정하므로 유형의 조건이 아닙니다.

##### 노드형 vs 일반형

두 유형의 특성을 비교해 확정합니다. (★ = 결정적 신호)

| 비선형 신호 · 일반형 | 선형 신호 · 노드형 |
| --- | --- |
| 순서 없이 독립적으로 처리 가능 | ★ 정해진 순서·절차를 거쳐야 완료 |
| 단계 간 의존이 없음 | ★ 이전 단계가 끝나야 다음 단계 가능 (선행 의존) |
| 고객 고지·동의 국면 없음 | ★ 진행 중 고객 고지·인지·동의 국면 있음 |
| 단계 간 정보가 서로 영향을 주지 않음 | 앞 단계 결과가 뒤 단계 입력·조건이 됨 |
| 한 화면에서 조회·등록·수정 반복 | 단계마다 보여 줄 정보·액션이 크게 달라짐 |
| 진행 위치를 따로 인지할 필요 없음 | 중단·재개·현재 단계 인지가 중요 |

**판정 규칙.**
① 선형 ★ 신호가 하나라도 강하게 해당하면 **노드형**입니다.
② ★가 없으면 양쪽 체크 수를 비교해 선형 신호가 더 많으면 **노드형**입니다.
③ 양쪽이 팽팽하고 ★도 없으면 **일반형**입니다.

- **고객 고지가 왜 결정적인가요**: 고지는 시점을 증명해야 하는 행위입니다. ‘이 시점에 이것을 알렸다’가 기록으로 남아야 하므로 단계를 흩어 놓을 수 없습니다.
- **단계의 수나 유무로 가르지 않습니다**: 몇 단계인지는 결과이지 기준이 아닙니다. 두 단계짜리라도 고객 고지 국면이 있으면 노드형이고, 입력 폼을 여러 단계로 쪼갠 것은 한 업무의 국면이라 일반형입니다. (이때는 [빅 폼](form-big.html)을 씁니다)
- **입력이 계속 커지면 선형인지 다시 봅니다**: 순서가 강제된다면 노드형이 맞습니다. 비선형인데 입력만 큰 경우는 [빅 폼](form-big.html)으로 처리합니다.
- **정책으로 특정 유형이 정해져 있으면 그 유형을 우선 검토합니다**: 위 판정 결과와 다르더라도 정책이 앞섭니다.

#### 3. 연결 기준

업무를 최소 단위로 나눠 구성하면 페이지 하나하나는 명확해지지만, 사용자가 전체적인 맥락에서 해당 업무를 찾아가야 하는 불편이 발생합니다.
**업무 사이를 연계해 이 맥락을 잇습니다.**

맥락의 성격에 따라 아래 셋 중 하나를 고릅니다.

워크스페이스특정 업무 대상(고객 · 계약 · 상품 등) 하나에 대한 대시보드를 제공하는 화면입니다.
그 대상에 걸린 연관 업무의 현황을 한눈에 요약해 보여 주고 각 세부 업무로 진입시키는 허브(Hub) 역할을 합니다.

Task Flow여러 단계의 완결이 차례대로 이어질 때 씁니다.
각 단계에 순서를 걸어 사용자가 현재 위치를 인지하며 진행하게 합니다.

Cross-linking순서 없이 필요한 자리에서 다른 업무를 열 때 씁니다.
비선형으로 전개되는 업무 흐름을 효율적으로 오갈 수 있게 합니다.

- **Task Flow와 Cross-linking은 혼용될 수 있습니다**: 한쪽만 쓰이기도 하고 둘이 섞여 쓰이기도 합니다. Task Flow로 진행하는 도중에 그 흐름에 없는 업무가 필요하면 그 자리에서 Cross-linking으로 엽니다.

Task Flow와 Cross-linking의 규격은 [업무 연결](work-connect.html)이 규정합니다.

##### 업무 슬롯 페이지

일부 레거시 화면은 업무 페이지를 나누는 것이 아니라, 한 페이지에서 수십·수백 개의 업무를 셀렉트 박스로 선택하고 하단 컨텐트를 로딩하는 형태를 가지고 있습니다.
그런 업무 페이지는 메뉴 검색이 불가능하고, Task Flow를 비롯해 신규 플랫폼이 제공하는 각종 편의 기능과 AI 보조 기능에 접근하는 데 제한이 발생합니다.
업무 슬롯 페이지는 기존 사용 경험을 지키면서 신규 플랫폼의 이점을 얻습니다.

- 이 페이지가 직접 제공하는 것은 업무를 고르는 셀렉트와 조회조건뿐입니다.
- 실제 업무는 원자화된 업무 페이지를 아이프레임 슬롯에 크롬리스로 불러옵니다.
- 조회조건 값은 [Cross-linking](work-connect.html)처럼 세션에 남아 슬롯 안 업무로 넘어가므로, 안에서 같은 조건을 다시 묻지 않습니다.
- 슬롯에 들어간 업무도 독립 페이지라, 메뉴나 [Cross-linking](work-connect.html)으로 단독으로 열면 자기 조회조건을 갖춘 온전한 화면이 됩니다.
- 신규 시스템으로의 유연한 전환을 위한 과도기 패턴이며, 처음부터 업무를 나눠 설계할 수 있으면 쓰지 않습니다.

조회조건에서 처리구분과 상세구분을 고르면 해당 업무 페이지가 아래 슬롯에 들어옵니다.

업무 슬롯 페이지 · 기업서비스 변경새 탭에서 크게 보기※ 예시 이미지 — 레이아웃/디자인은 확정 아님. 패턴 구조만 참고.위 슬롯에 들어가는 원본 페이지입니다. 슬롯을 거치지 않고 메뉴나 Cross-linking으로 열면 이렇게 셸과 자기 조회조건을 갖고 그대로 동작합니다.

슬롯에 끼워지는 업무 · 중계선매개번호변경새 탭에서 크게 보기※ 예시 이미지 — 레이아웃/디자인은 확정 아님. 패턴 구조만 참고.
#### Do / Don't

###### Do · 이렇게 합니다

- 요구사항을 최소 단위로 분해한 뒤 대상·맥락 두 기준으로 그룹화합니다.
- 이미 존재하는 업무는 새로 만들지 않고 연결로 설계해 범위에서 제외합니다.
- 업무 단위로 판정된 것에는 자체 URL을 가진 페이지를 할당합니다.
- 업무 이름은 대상과 목적이 드러나게 붙입니다.
- 특수형인지를 가장 먼저 묻고, 선형 ★ 신호가 하나라도 있으면 노드형으로 편성합니다.
- 유형은 완전한 권한을 가진 상태로 판정합니다.
- 정책으로 유형이 정해져 있으면 그 유형을 우선 검토합니다.
- 순서가 없는 관계는 Cross-linking으로 걸어 둡니다.
- 레거시 화면을 옮길 때도 업무는 나누고, 쓰는 방식만 업무 슬롯 페이지로 맞춥니다.

###### Don't · 이건 피합니다

- 분해하기 전에 페이지 개수부터 정하지 않습니다.
- 서로 다른 대상을 다루는 일을 한 페이지에 담지 않습니다.
- 목적이 다른 일을 같은 대상이라는 이유로 한 페이지에 담지 않습니다.
- 업무를 팝업이나 탭 컨텐트로 규정하지 않습니다.
- 단계의 수나 유무로 유형을 가르지 않습니다.
- 권한으로 좁혀진 모습이나 CRUD 요소의 개수로 유형을 판정하지 않습니다.
- 특수형이라고 해서 값을 주고받는 연결까지 끊지 않습니다.
- 슬롯에 끼운 업무 화면에 조회조건을 다시 두지 않습니다.
- 슬롯에서만 열리는 화면을 만들지 않습니다.
- 새로 설계하는 업무를 업무 슬롯 페이지로 묶지 않습니다.
