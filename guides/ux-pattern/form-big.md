폼 그룹이 여럿이고 조건부 연동이 많은 대형 입력을, 기본 폼의 원리를 유지한 채 한 화면에서 다루는 패턴입니다.
입력은 왼쪽 폼에, 결과는 오른쪽 실시간 프리뷰에 두고 한 페이지 안에서 완결합니다.

#### 개요 · 언제 쓰나요?

빅 폼은 입력 항목이 많고 선택에 따라 필요한 항목이 달라지는 대형 폼입니다.
[입력 폼 모듈 공통 정의](form-basic.html)의 두 원리(입력·결과 분리, 한 페이지 완결)를 그대로 유지하되, 규모가 커졌을 때 이를 지키기 위한 구조를 규정합니다.
입력 폼 모듈 공통 정의가 다루기 어려운 다중 폼 그룹·조건부 연동 입력을 대상으로 합니다.

###### ✓ 이럴 때 사용합니다

- 입력 항목이 많아 폼 규모가 큰 경우
- 노드로 단계를 나눌 수 없어 한 화면에서 처리해야 하는 경우

###### ✕ 다른 패턴을 사용합니다

- 입력 항목이 적은 화면 → 입력 폼 모듈 공통 정의
- 목록에서 여러 행을 다루는 화면 → Grid Based Patterns
- 여러 단계로 나눌 수 있는 업무 → [노드형 화면](layout-node.html)

기억할 점입력이 이 정도로 커지면 여러 단계로 나누는 노드형 화면이 더 맞는 경우가 많습니다.
빅 폼은 노드를 사용할 수 없어 한 화면에서 처리해야 할 때 권장하는 패턴입니다.

핵심 원칙빅 폼도 입력 폼 모듈 공통 정의와 같은 원리를 따릅니다.
입력 항목만 폼 컨트롤로 두고 결과는 표시 요소로 나타내며(분리), 제출 결과까지 한 페이지 안에서 확인합니다(완결).
작업 시간이 길어 컨텍스트 유지가 중요하므로, 화면을 벗어나거나 맥락을 끊는 이동·전환은 자제합니다.
커진 규모는 새 원리가 아니라 구조(폼 그룹·조건부 노출·프리뷰)로 감당합니다.

#### 구성요소

1. 조회조건 모듈 (화면 최상단, 선택)공통 [조회조건 모듈](search-conditions.html)을 폼 구성 결정 용도로 쓴 것입니다. 검색이 아니라 사전 구분이므로 타이틀을 용도에 맞게 바꾸며, 여기서 고른 값이 하위 폼 그룹·필드의 노출을 결정합니다. 폼 구성을 미리 나눌 필요가 없으면 생략합니다.
2. 입력 모듈 (좌)폼 컨트롤만 두는 넓은 입력 영역입니다. 여러 폼 그룹으로 묶고, 헤더의 그룹 칩으로 이동합니다.
3. 결과 · 프리뷰 모듈 (우)폼 컨트롤 없이 표시 요소만 두는 영역입니다. 입력에 실시간 연동해 금액·요약·미충족 항목을 보여 줍니다. 표현 방식(상태 카드·읽기 전용 텍스트·프리뷰 등)은 화면 성격에 맞게 정하며, 목업은 한 가지 예일 뿐입니다.
4. 하단 상태바각 모듈 하단에 부가 정보나 연관 작업 링크를 두는 보조 영역입니다.

액션·CTA 배치와 컨텐트 모듈 구조는 컨텐트 모듈 개요 표준을 따릅니다.기억할 점[입력 폼 모듈 공통 정의](form-basic.html)는 입력과 결과의 좌우·상하 배치를 가리지 않지만, 빅 폼은 좌우 배치를 전제합니다.
입력이 길어 스크롤되므로, 프리뷰가 계속 보이도록 입력을 왼쪽에 두고 결과·프리뷰를 오른쪽 고정 레일로 둡니다.

#### 폼 그룹

빅 폼의 핵심은 입력을 폼 그룹으로 묶어 제공하는 것입니다.
그룹으로 묶지 않은 대형 폼은 한눈에 훑고 접근하기 어려우므로, 그룹핑하지 않을 것이면 빅 폼으로 만들지 않습니다.

폼 그룹을 아코디언(열고 닫기) 형태로 두면 여러모로 유용합니다.

- 복잡한 폼을 접어 두고 필요한 그룹만 펼쳐, 전체를 간추려 볼 수 있습니다.
- 절차형 입력이 필요하면 순서대로 펼치며 단계처럼 진행할 수 있습니다.
- 화면 성격에 따라 처음 펼침·접힘이나 한 번에 하나만 열기 등을 설정할 수 있습니다.

배치는 다음을 따릅니다.

- 폼 그룹은 박스 프레임(테두리·라운드·회색 헤더) 없이 구분선만 두어, 모듈 박스 안에서 이중 박스가 되지 않게 합니다.
- 입력 모듈 헤더에 그룹 칩을 두어 앵커 내비로 씁니다. 칩을 누르면 해당 그룹으로 이동합니다.
- 조건부로 꺼진 그룹은 칩에서도 자동으로 제외합니다.

#### 폼 구성 컴포넌트

폼을 구성하는 일반 입력 항목의 종류와 사용법은 UI 컴포넌트 가이드를 따릅니다.
빅 폼에서 따로 다루는 것은 폼 안에서 바로 처리하기 어려운 복잡한 선택·입력입니다.
현행 시스템은 이를 대부분 팝업으로 처리해 팝업이 지나치게 많아지는 문제가 있었으므로, 다음 컴포넌트로 폼 안에 편성해 컨텍스트를 유지하면서 팝업 남발을 줄입니다.

- **[사이드 패널](option-panel.html)**: 폼 안에서 구현하기 어려운 복잡한 선택·입력을 우측 패널에서 처리합니다.
- **[인라인 편집 테이블](grid-inline.html)**: 화면을 벗어나지 않고 다건 데이터를 입력·수정합니다. 저장·행 추가·건수는 표 하단 상태바에서 처리하고, 표 저장은 로컬 액션이므로 우상단 CTA와 구분해 주 버튼으로 만들지 않습니다.

기억할 점팝업과 사이드 패널의 선택 기준은 공통 정책을 따릅니다.
다만 빅 폼에서는 입력 컨텍스트가 끊기지 않도록 사이드 패널을 우선 권장합니다.

#### 실시간 프리뷰 · 검증

결과 모듈은 입력에 실시간으로 연동해 결과를 즉시 확인할 수 있게 합니다.
항목이 많아 채우지 않은 항목을 놓치기 쉬우므로, 일반 폼보다 미충족 항목을 더 적극적으로 알립니다.

- 신청 내용을 요약해 롤업하고, 제출 전 미충족 필수 항목을 목록으로 보여 줍니다.
- 조건부로 꺼진 항목은 검증에서 제외하고, 노출된 필수 항목만 미충족으로 셉니다.

#### 제출 · 완결

- 제출 CTA는 제출 가능 조건을 모두 충족할 때까지 활성화하지 않습니다. 노출된 필수 항목이 미충족이면 제출할 수 없습니다.
- 제출 가능 여부(남은 미충족 항목)를 사용자에게 노출합니다. 분할 캡슐(왼쪽에 미충족 건수·제출 가능 요약, 오른쪽에 제출 버튼)은 한 가지 방법이며, 같은 목적이면 다른 UI로 대체해도 됩니다.
- 제출하면 확인 팝업으로 한 번 더 확인한 뒤, 같은 페이지에서 접수완료로 닫습니다. 다른 업무 페이지로 이동하지 않습니다.

##### 임시저장

빅 폼은 작업 시간이 길어 업무를 처리하다 중간에 멈춰야 하는 경우가 생깁니다.
이때를 위해 CTA 왼쪽에 ‘임시저장’ 버튼을 둘 수 있습니다.

- **필수 값을 다 채우지 않아도 누를 수 있습니다**: 지금까지 받은 값을 확정하지 않은 채 남겨 둡니다.
- **특이 데이터 입력 컴포넌트를 쓰는 폼에는 임시저장을 두기를 강력히 권장합니다**: [특이 데이터 입력](ui-comp-input-extended.html)의 컴포넌트(입력 스택 · 옮겨 담기 · 확인 필드 등)를 쓰는 폼은 받는 값이 많고 경우가 복잡합니다. 입력한 내용을 놓치기 쉬우므로 중간에 남겨 둘 수단이 필요합니다.

#### 실제 예시

가입 구분에 따라 폼 그룹이 조건부로 바뀌고, 왼쪽 입력이 오른쪽 프리뷰로 실시간 반영되는 신청 접수 화면입니다.

빅 폼 · 신청 접수 화면새 탭에서 크게 보기※ 예시 이미지 — 레이아웃/디자인은 확정 아님. 패턴 구조만 참고.예시 화면은 실제 화면이 아니라 이해를 돕기 위해 모두 가상으로 빌드한 페이지입니다.브랜드·카탈로그·개인정보 등 실데이터성 값은 익명화했고, 구조와 조건부 연동을 읽기 쉽도록 폼 그룹명·필드 라벨 등은 약하게 익명화했습니다.
#### Do / Don't

###### Do · 이렇게 합니다

- 입력은 폼에, 결과·프리뷰는 표시 요소로 분리합니다.
- 큰 입력은 폼 그룹으로 묶고, 필요한 그룹·필드만 조건부로 노출합니다.
- 복잡한 선택·입력은 [사이드 패널](option-panel.html)·[인라인 편집 테이블](grid-inline.html)로 폼 안에서 처리합니다.
- 미충족 항목을 알리고, 제출까지 같은 페이지에서 완결합니다.
- 특이 데이터 입력 컴포넌트를 쓰는 폼에는 CTA 왼쪽에 ‘임시저장’을 둡니다.

###### Don't · 이건 피합니다

- 조회·결과 항목을 폼 컨트롤로 표시하지 않습니다.
- 입력을 그룹으로 묶지 않고 한 덩어리로 늘어놓지 않습니다.
- 쓰지 않는 그룹·필드를 처음부터 모두 노출하지 않습니다.
- 맥락을 끊는 팝업 남발이나 페이지 이동을 만들지 않습니다.
