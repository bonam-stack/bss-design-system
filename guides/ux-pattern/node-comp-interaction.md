상담사와 고객이 주고받아야 진행되는 노드 모듈입니다.
핵심 동작·상태와 CTA를 중심으로, 특이사항·요청 맥락·가이드 정보를 필요에 따라 더합니다.

#### 개요 · 언제 쓰나요?

상호작용형은 노드 모듈 유형의 하나입니다.
상담사와 고객이 주고받아야 진행되는 노드 모듈을 어떤 구조로 설계하는지 규정합니다.
요청을 보내고 · 응답을 기다리고 · 반영하는 흐름으로 이루어지며, 한쪽만으로는 끝낼 수 없고 고객의 응답·처리가 진행 조건일 때 이 패턴을 씁니다.

###### ✓ 이럴 때 사용합니다

- 본인 인증·전자서명처럼 고객이 직접 처리해야 진행될 때
- 인증번호처럼 고객이 받은 값을 받아 적어 인증할 때
- 약관을 고지하고 고객 동의를 받아야 다음으로 넘어갈 때

###### ✕ 다른 노드 모듈 유형을 사용합니다

- 값을 읽고 확인만 하면 → 조회형
- 값을 고르거나 넣거나 고치게 하면 → 선택형·입력형
- 고객이 원래 아는 정보를 불러 주어 받아 적기만 하면 → 입력형

##### 기본 틀

상호작용형 노드 모듈은 위에서 아래로 특이사항(선택) · 요청 맥락(선택) · 핵심 동작·상태 · 가이드 정보(선택) · CTA를 쌓습니다.
요청 맥락을 먼저 보여 주고, 그 아래 핵심 동작·상태 자리에서 요청 전송·응답 대기·인증·동의 같은 상호작용이 일어납니다.

1. 특이사항 (선택 · 최상단)고객 응대 상태처럼 먼저 봐야 할 안내를 콜아웃으로 알립니다. 기본은 두지 않고, 꼭 필요할 때만 표시하는 옵션 요소입니다. 핵심 동작·상태를 읽는 시야를 해치지 않도록 간결하게 씁니다.
2. 요청 맥락 (선택)무엇을 · 누구에게 · 어떤 수단으로 요청하는지를 담습니다. 필수가 아닌 옵션 요소이며, 정보 요약을 기본으로 씁니다.
3. 핵심 동작·상태이 모듈이 다루는 상호작용입니다. 요청 전송·응답 대기·인증·동의 등 내용에 따라 표현이 달라집니다. 필요하면 여러 구성요소를 함께 편성할 수도 있습니다.
4. 가이드 정보 (선택)이 모듈의 사용법이나 놓치기 쉬운 응대 규칙을 짚어 줍니다. 필수가 아닌 옵션 요소입니다. AI 안내로 채울 수도 있고, 정해진 안내를 그대로 둘 수도 있습니다.
5. CTA‘요청 전송’·‘다음’처럼 다음 동작을 실행하는 버튼입니다. 모든 노드 모듈에 공통이며 맨 아래로 분리합니다.

특이사항 → 요청 맥락 → 핵심 동작·상태 → 가이드 정보 → CTA 순으로 쌓은 골격입니다.

#### 구성요소

핵심 동작·상태 자리에 넣는, 고객과의 상호작용을 일으키는 표현입니다.
인증번호 발송·약관 동의·수단별 인증처럼 고객의 응답·처리가 있어야 진행되는 표현이 이 패턴의 고유 표현입니다.
같은 속성끼리 묶어 두었습니다.
인증을 수행하는 표현이 먼저 오고, 고지·동의 표현, 대기·현장 안내 순으로 이어집니다. (진행 상태·검증 리스트처럼 처리 상태를 보여 주는 표현은 처리형에서 가져와 씁니다. → 처리형 참고)

##### 인증번호 입력

고객에게 인증번호를 발송하고, 고객이 불러 주는 번호를 상담사가 받아 적어 인증합니다. 발송하면 입력칸이 열리고 제한 시간이 함께 표시됩니다.
**규칙** 인증을 마치기 전에는 다음으로 넘어가지 않고, 제한 시간이 지나면 재발송을 둡니다.

##### 수단별 인증

여러 인증 수단을 아코디언으로 나눠 두고, 고객 상황에 맞는 하나를 골라 진행합니다.
**규칙** 하나를 완료하면 나머지 수단은 잠가 중복 인증을 막고, 완료해야 다음으로 넘어갑니다.

##### 약관 고지·동의

상담사가 약관을 고객에게 고지하고 직접 체크합니다. 약관명을 누르면 옆에서 핵심 요약이 열려 그대로 읽어 줍니다.
**규칙** 단순 링크 전송이 아니라 상담사가 고지하고 체크하며, 필수 약관을 전부 체크해야 다음으로 넘어갑니다.

##### 고지 안내

상담사가 고객에게 반드시 고지해야 하는 내용을 타이틀 + 내용 한 카드로 그대로 안내합니다. 인증·동의 게이트 없이 고지만 하고 확인받습니다.
**규칙** 고지 문구는 규격 그대로 담고 임의로 고치지 않습니다. 최상단 노란 콜아웃은 이 Atom에 포함하지 않습니다.

##### 대기·현장 안내

요청을 보내기 전 무엇을 하는 모듈인지, 또는 현장에서 무엇을 하는지를 아이콘과 함께 크게 안내합니다.
검색 안내와 현장 서명 안내처럼 담는 아이콘·문구가 달라집니다.

**규칙** 아직 값이 없는 자리(요청 전·현장 대면)에만 쓰고, 진행 상태는 처리형의 처리 상태 표현으로 따로 보여 줍니다.

#### 핵심 동작 · 상태

##### 요청 → 대기 → 반영

- 상호작용은 요청 전송 → 응답 대기 → 반영 순서로 흐릅니다. 요청 맥락을 먼저 보여 주고, 요청을 보낸 뒤 응답 상태로 진행을 알립니다.
- 반영이 일어나는 자리는 요청 방식에 따라 세 갈래로 나뉩니다.
  - 고객 직접 처리: 상담사가 요청을 보내면 고객이 자기 기기에서 처리하고, 시스템이 자동으로 반영합니다. (예. 본인 인증·전자서명)
  - 중계 기입: 상담사가 발송하고, 고객이 받은 값을 불러 주면 상담사가 받아 적어 인증합니다. (예. 인증번호)
  - 현장 대면: 원격 발송이 아니라 팝업을 띄워 고객이 그 자리에서 직접 처리합니다. (예. 대리점 서명 패드)
- 가장 단순한 형태(인증 요청 + CTA)에서 출발해 요청 방식에 맞는 표현만 더합니다.
- 구분선은 요청 맥락과 필수 정보 사이에만 넣습니다. 필수 정보끼리는 제목으로 나뉘어도 넣지 않고, 가이드 정보 앞뒤에도 넣지 않습니다. CTA만 맨 아래로 분리합니다.
- 요청 맥락의 영역 제목은 선택입니다. 제목 없이 내용만 두어도 되고, 내용만으로 무엇인지 읽히면 제목을 넣지 않습니다.

##### 상태 표시

- 요청 진행 상태(대기·진행·완료·실패)는 처리형의 처리 상태·검증 리스트 표현을 그대로 가져와 보여 줍니다. (→ 처리형 참고)
- 인증을 마쳐야 다음으로 넘어가는 경우, 완료 전에는 다음 버튼을 비활성으로 둡니다. (예. 인증번호·약관·수단별 인증)

표현별 규칙은 위 구성요소의 각 표현 설명에 함께 적었습니다.
##### 진행 표시

- 노드 모듈이 여러 단계(페이지)나 경로(탭)로 진행되면, 단계 표시는 모듈 안이 아니라 액션바에 둡니다. (예. 액션바 타이틀 ‘가족 인증 (1/2)’)

#### Do / Don't

###### Do · 이렇게 합니다

- 노드 안에서의 클릭은 1~2회로 권장합니다. 한 노드에 과도한 단계·클릭을 만들지 않습니다.
- 가장 단순한 형태(인증 요청 + CTA)에서 출발해 요청 방식에 맞는 표현만 더합니다.
- 요청 맥락을 먼저 보여 주고, 요청 → 대기 → 반영 순서로 흐르게 합니다.
- 인증을 마쳐야 다음으로 넘어가는 경우, 완료 전에는 다음 버튼을 비활성으로 둡니다.
- 진행 상태·검증 리스트는 처리형의 표현을 그대로 가져와 씁니다.

###### Don't · 이건 피합니다

- 고객이 원래 아는 정보를 불러 주어 받아 적기만 하는 모듈을 상호작용형으로 두지 않습니다. (→ 입력형)
- 상태 표시·검증 리스트 표현을 상호작용형 고유 구성요소로 두지 않습니다. (→ 처리형)
- 가이드 정보·특이사항을 습관적으로 넣지 않습니다.
