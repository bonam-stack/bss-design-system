값을 입력하는 항목과 조회·결과로 확인하는 항목을 분리하는, 폼 중심 화면의 기본 패턴입니다.
사용자가 값을 채우는 자리에만 폼 요소를 두어 입력과 결과가 뒤섞이지 않게 합니다.

#### 개요 · 언제 쓰나요?

기본 폼은 값을 입력해 처리(저장·송신)하는 폼 중심 화면입니다.
기존 화면은 사용자가 채우는 항목과 조회로 확인만 하는 항목을 똑같은 폼 박스로 표현해, 무엇을 입력해야 하고 무엇이 결과인지 구분하기 어려웠습니다.
이 패턴의 핵심은 입력받을 항목과 조회·결과로 보여줄 항목을 분리하는 것입니다.
분리 자체가 요지이며, 좌우 배치든 상하 배치든 레이아웃 형태는 규칙이 아닙니다.

###### ✓ 이럴 때 사용합니다

- 값을 입력해 처리(저장·송신)하는 폼 중심 화면
- 입력한 값에 따라 결과나 프리뷰를 같은 화면에서 바로 확인하는 흐름

###### ✕ 다른 패턴을 사용합니다

- 다중 섹션·조건부 연동이 많은 대형 입력 → [빅 폼](form-big.html)
- 목록에서 여러 행을 다루는 화면 → Grid Based Patterns

핵심 원칙입력받을 항목과 조회·결과로 보여줄 항목을 분리합니다.
사용자가 값을 채우는 자리에만 폼 요소를 두고, 확인만 하는 항목은 폼 컨트롤로 두지 않아 편집 대상과 혼동되지 않게 합니다.

#### 구성요소

1. 폼 영역사용자가 값을 입력하는 영역입니다. 폼 요소(텍스트 인풋·셀렉트·데이트피커)는 이 영역에 둡니다.
2. 결과 · 프리뷰 영역폼 영역과 분리해, 입력한 값에 따라 결과나 프리뷰를 바로 확인하는 영역입니다. 표현 방식(상태 카드·읽기 전용 텍스트·프리뷰 등)은 화면 성격에 맞게 정하며, 목업은 한 가지 예일 뿐입니다.
3. 조회조건 모듈 (선택)폼 중심 페이지에서 반드시 두는 요소는 아닙니다. 검색 조건에 따라 폼의 주 구성이 달라지는 경우처럼, 대상·구성을 먼저 정해야 할 때 화면 최상단에 둡니다. 세부 규칙은 조회조건 패턴을 따릅니다.
4. 액션 · CTA저장·송신 등 처리 버튼입니다. 배치는 컨텐트 레이아웃 표준을 따라 컨텐트 모듈 우상단에 둡니다.
5. 하단 상태바부가 정보(연락처 등)나 연관 메뉴 안내 등을 두는 보조 영역입니다.

액션·CTA의 배치와 컨텐트 모듈 구조는 컨텐트 모듈 개요 표준을 따릅니다.
#### 입력 항목과 조회·결과 항목의 분리

이 패턴의 핵심은 데이터 항목을 성격에 따라 나누는 것입니다.
같은 값이라도 사용자가 채우는 값인지, 조회로 확인하거나 처리 결과로 채워지는 값인지에 따라 표현을 달리합니다.

입력 항목 (폼 요소 사용)사용자가 값을 채우거나 고르는 항목입니다.
조회로 값이 미리 채워졌더라도 수정할 수 있으면 여기에 포함해, 텍스트 인풋·셀렉트·데이트피커 등 폼 컨트롤로 둡니다. (예. 증빙자료 선택, 발급일 입력)

조회·결과 항목 (폼 요소 비사용)수정될 개연성이 없이 확인만 하는 항목입니다.
폼 컨트롤이 아니라 화면에 맞는 표시 방식으로 나타내, 편집 대상과 구분합니다. (예. 처리결과, 처리일, 영업장, 처리자)

유의사항판단 기준은 항목이 조회성인지가 아니라 수정 가능성입니다.
입력 항목과 똑같이 생긴 비활성(disabled) 폼 컨트롤이 섞이면 무엇을 채워야 하는지 흐려지고, 편집할 수 있는 항목으로 오인됩니다.
단순히 조회되는 데이터까지 폼으로 표현하는 것은 현행 SWING의 대표적인 혼란 요인 중 하나이며, 이 패턴에서 우선 개선하는 지점입니다.

예외. '수정할 수 없는 값'임을 특별히 강조해야 하는 경우에는, 비활성 폼 컨트롤로 표현하는 등 이 지침을 반드시 따르지 않아도 됩니다.
#### 한 페이지 안에서의 완결

폼 중심 페이지는 입력에서 결과 확인까지 한 페이지 안에서 완결되어야 합니다.

핵심 원칙폼을 제출하면 그 결과를 같은 페이지 안에서 바로 확인할 수 있어야 합니다.
제출과 동시에 다른 업무 페이지로 이동시키는 흐름은 사용하지 않습니다.

- 레이아웃은 '입력 → 결과 확인'이라는 사용자의 의식 흐름에 따라 조성합니다.
- 컨텐트 모듈의 배치는 [컨텐트 모듈 개요](layout-content.html)를 따릅니다.

결과 영역의 상태(Loading · Empty · Error 등) 표현은 디자인 가이드를 참조합니다.
#### 실제 예시

폼 영역과 결과 영역을 분리하고, 조회·결과 항목은 폼 컨트롤이 아닌 표시 요소로 나타낸 화면입니다.
이 목업은 두 영역을 좌우로 나눈 한 가지 예이며, 분리가 핵심이지 좌우 배치가 규칙은 아닙니다.

#### Do / Don't

###### Do · 이렇게 합니다

- 입력받을 항목과 조회·결과로 보여줄 항목을 분리합니다.
- 폼 요소는 사용자가 값을 입력하는 자리에만 둡니다.
- 입력한 값에 따라 결과·프리뷰를 같은 화면에서 바로 확인할 수 있게 합니다.
- 조회·결과 항목은 화면 성격에 맞는 표시 방식으로 나타냅니다.
- 조회조건은 검색 조건으로 폼 구성을 정해야 할 때처럼, 필요할 때만 둡니다.
- 레이아웃은 입력 → 결과 확인의 흐름에 따라 조성합니다.

###### Don't · 이건 피합니다

- 폼을 제출하면 곧바로 다른 업무 페이지로 이동시키지 않습니다. (결과는 같은 페이지에서 확인합니다)
- 확인만 하는 항목을 비활성 입력창·셀렉트로 표시하지 않습니다.
- 입력 항목과 조회·결과 항목을 같은 폼 박스로 뒤섞지 않습니다.
- 쓰지 않는 입력까지 처음부터 모두 노출하지 않습니다.
- 좌우 배치 같은 특정 레이아웃을 규칙으로 강제하지 않습니다.
- 조회조건을 모든 폼 화면에 습관적으로 넣지 않습니다.
